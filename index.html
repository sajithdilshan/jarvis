THE LOOP

How it works

A Temporal cron schedule wakes Jarvis on an interval. It fans out to every source agent in parallel, then splits the results down two paths: deterministic autonomous action, and LLM reasoning. Everything lands in a live briefing.

TWO WORKFLOWS

What Jarvis actually is

Everything Jarvis does runs as one of two durable Temporal workflows. The scheduled workflow is the "always watching" loop that polls and acts on its own. The interactive workflow is the conversation. Both survive restarts and retry failed steps automatically.

◷ AUTONOMOUS LOOP

MainAgentWorkflow

One run per cron tick (default: every 15 min, work hours).

  1. Stamp the window. Record now as the upper bound; read the poll watermark (last clean run) as the lower bound — exactly "what changed since we last succeeded." First run → last 24h.
  2. Fan out in parallel. Every poll=True source agent runs as its own activity with its MCP toolset, returning a schema-validated summary. Failures are isolated per source.
  3. Act + reason at once. The deterministic permission engine performs allowed actions → "did"; the synthesize agent (LLM) reasons over everything → "noticed" / "ask".
  4. Publish. Entries are written to briefing_log; a Postgres NOTIFY pushes a refresh to every open browser.
  5. Advance only on a clean run. If any source failed, the watermark stays put so the next run re-covers that window — no missed data.

Trigger one by hand: scripts/trigger_poll.py

◈ THE CONVERSATION

InteractiveChatWorkflow

One long-lived workflow backs the whole chat UI.

  1. Message in. A chat message or dashboard click signals the running workflow — no per-message scheduling overhead.
  2. Context assembly. Recent conversation history and unresolved dashboard alerts are prepended, so "yes, do the rest" works.
  3. Lazy MCP tools. Rather than attach every toolset upfront, the agent lists servers and calls any tool on demand — keeping the prompt small.
  4. Stream the reply. Tokens stream to the browser over the WebSocket relay; history, memory and telemetry persist after the reply is on screen.
  5. Bounded history. Continues-as-new every 50 messages; completes after 2h idle and respawns on the next message.

It can grant / revoke / refine permissions — that's how the loop learns what it may do.

DESIGN PRINCIPLES

◆ Agents are plugins

Any folder under agents/sources/ that exports a SPEC is auto-discovered. A source is just a prompt, a schema, and an MCP server name — adding one needs no wiring.

◆ Two model tiers

Scheduled agents use a cheap default_model; chat uses a capable interactive_model. Specs are provider-agnostic: bedrock:, openai:, ollama:.

◆ Poll watermark

The "last successful poll" timestamp only advances when no source failed — so a failed source re-covers its exact window on the next run. No gaps, no dupes.

◆ Tool gating

Each MCP server is defined once with a deny_tools list that blocks dangerous tools (delete, send) from both exposure and invocation. Safe by default.

EXTEND

Add a new source agent

Agents are plugins. AgentRegistry auto-discovers any folder under agents/sources/ that exports a SPEC — no central list to edit. Drop in a folder and it joins the scheduled fan-out.

Declare its MCP server (if it needs one)

Add the server once to mcp/servers.yaml. Reference secrets as ${VAR} and gate dangerous tools with deny_tools. jarvis-auth status picks up the new token requirement automatically.

linear:
  type: stdio
  command: "npx"
  args: ["-y", "linear-mcp-server"]
  env:
    LINEAR_API_KEY: "${LINEAR_API_KEY}"
  deny_tools:
    - delete_issue

Create the agent folder

Add src/jarvis/agents/sources/<name>/. The folder name must match SPEC.name — the registry enforces it.

agents/sources/linear/
├── __init__.py    # exports SPEC (the contract)
├── prompt.md      # the agent's system prompt
├── schema.py      # structured result (Pydantic)
└── tools.py       # optional extra Python tools

Define the result schema

The field named by items_key must hold a list[ItemModel]. Its per-item fields become the match-targets for permissions and chat — name them well.

class LinearIssue(BaseModel):
    title: str
    state: str
    url: str
    requires_action: bool = False
    raw_data_id: str

class LinearSummary(BaseModel):
    issues: list[LinearIssue] = []

Export the SPEC

In __init__.py, wire prompt + schema + MCP server together.

SPEC = AgentSpec(
    name="linear",                # == folder name
    prompt=load_prompt(__file__),
    result_type=LinearSummary,
    items_key="issues",           # the actionable list
    mcp_servers=["linear"],        # from servers.yaml
    model_env="JARVIS_TOOL_AGENT_MODEL",
    # poll=True (default) → joins scheduled runs
)

Restart — done

The agent is discovered automatically: it joins the poll, its schema is exposed to the synthesize and interactive agents, and standing permissions can target its fields. No other code changes needed.

GET RUNNING

Setup & run

Prerequisites: Docker, uv (Python 3.13), an LLM provider (AWS Bedrock by default, OpenAI, or local Ollama), and tokens for the sources you want.

1 — CONFIGURE

# copy the env template, fill in providers + tokens
cp .env.example .env

# Bedrock is opt-in — for OpenAI/Ollama leave it off.
# To use Bedrock, set in .env then `aws sso login`:
AWS_BEDROCK_ENABLED=1
AWS_PROFILE=your-sso-profile

# manage MCP credentials (discovers reqs from servers.yaml)
uv run jarvis-auth status
uv run jarvis-auth set GITHUB_TOKEN ghp_...
uv run jarvis-auth gmail      # browser OAuth
uv run jarvis-auth atlassian

2 — LAUNCH

# build + start everything, tail app logs
./start.sh
./start.sh --build   # force image rebuild
./start.sh --infra   # infra only, app local:
uv run python -m jarvis.main

./stop.sh            # data preserved
